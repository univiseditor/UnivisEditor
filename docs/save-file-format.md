# Save File Format

Status: Active supporting note. Kept alongside the cleanup roadmap because it documents the persisted save-file contract rather than the runtime-cleanup sequence.

## Summary

UnivisEditor now saves graphs through a versioned save-file envelope instead of writing raw
`GraphDocument` JSON directly.

The active on-disk format is:

- `format = "univis.graph"`
- `format_version = 1`

The envelope exists to make persistence more stable than the internal Rust types that happen to
back the editor at a given moment.

`meta.created_at` and `meta.updated_at` are currently stored as Unix timestamp strings in
milliseconds.

## Top-Level Shape

Every current graph save file is expected to look like this:

```json
{
  "format": "univis.graph",
  "format_version": 1,
  "generator": {
    "app": "UnivisEditor",
    "app_version": "0.1.0"
  },
  "meta": {},
  "document": {
    "nodes": [],
    "edges": [],
    "prefabs": [],
    "subgraphs": [],
    "view": {}
  }
}
```

## Why The Envelope Exists

The save-file envelope gives the project a stable contract for:

- future graph format migrations
- clear separation between persisted authoring data and runtime/editor state
- documenting which fields are part of the file format versus which are implementation detail

This lets `GraphDocument`, runtime components, and persistence internals evolve without requiring
the file format to mirror every internal refactor.

## Document Contract

The `document` payload currently stores only authored graph state:

- `nodes`
  - stable node id
  - `definition_id`
  - 2D editor position
  - `authored_inputs`
  - declared `input_count`
  - declared `output_count`
- `edges`
  - source endpoint
  - target endpoint
- `prefabs`
  - stable prefab id
  - display name
  - serialized `EntityValue`
- `subgraphs`
  - stable subgraph id
  - display name
  - nested graph document
- `view`
  - optional camera state
  - selected node ids

The file intentionally does not store:

- ECS entity ids
- runtime-resolved inputs
- compiled connectivity caches
- diagnostic caches
- transient UI overlay state

## Value Encoding

Authored node inputs are serialized as explicit tagged values rather than relying on Rust enum
layout details.

Current value kinds include:

- `none`
- `float`
- `int`
- `bool`
- `string`
- `vec2`
- `vec3`
- `vec4`
- `color`
- `entity`
- `tagged`

Example:

```json
{
  "kind": "color",
  "space": "srgba",
  "value": [1.0, 0.5, 0.2, 1.0]
}
```

`entity` values are also encoded through explicit DTOs rather than raw Bevy-facing structures.

## Entity Encoding

Scene-facing `EntityValue` payloads are written as:

- optional `name`
- `components`
- `children`

Each component is stored as an explicit tagged object such as:

- `transform`
- `sprite`
- `camera_2d`
- `text_2d`
- `visibility`
- `anchor`
- `custom`

This keeps scene persistence readable and migration-friendly.

## Save Metadata

The `meta` object currently holds:

- `created_at`
  - first known save timestamp for this file when available
- `updated_at`
  - last write timestamp produced by the current save path

When saving over an existing save-file `v1`, the current implementation preserves `created_at`
and refreshes `updated_at`. New files initialize both values on first write.

## Compatibility Rules

The current expectations are:

- new saves are always written as save-file `v1`
- load paths must accept the active save-file version
- load paths may also accept older legacy payloads and migrate them forward
- internal Rust types are free to evolve as long as save-file migration continues to preserve
  authored meaning

`format_version` is the authoritative on-disk version field.

## Legacy Migration

Legacy payloads are upgraded through `univis_editor_persistence::migrations`.

The current migration path supports:

- legacy `v0` graph payloads
- legacy raw `GraphDocument` JSON payloads

Both are upgraded into the save-file `v1` shape before the rest of the load pipeline proceeds.

This keeps parsing, migration, and DTO serialization separate:

- `format.rs`
  - save-file DTOs and serialization
- `migrations.rs`
  - legacy payload upgrades
- graph load/apply systems
  - validation and live graph reconstruction

## Stability Guidance

The project should treat these parts of the save file as contract-level fields:

- `format`
- `format_version`
- `document.nodes[*].id`
- `document.nodes[*].definition_id`
- `document.edges[*]`
- `document.prefabs[*].id`
- `document.subgraphs[*].id`

Other fields may still evolve, but changes should go through an explicit migration step instead of
silently changing serializer output.
